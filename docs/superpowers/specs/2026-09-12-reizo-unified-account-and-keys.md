# Reizo 统一账号、模型与密钥逻辑

日期：2026-09-12

状态：用户已确认产品边界；下列实现方案和验收项待落实。

## 1. 已确认的产品边界

Reizo 是唯一面向用户的入口。用户在 Reizo 完成登录、工作台对话、API Key 管理、余额与消费查询。

用户进一步确认：未来由 F:/selfProject/codex-proxy 替代 new-api。新项目提取所需网关功能，专注后台模型调用，只向管理员提供管理界面。new-api 是当前运行依赖及迁移来源，不是目标架构中必须保留的用户或计费系统。

下文第 3 至 11 节中的 new-api 绑定与接口描述属于当前状态或过渡方案；长期边界以第 12 节为准。

这份文档更新 2026-08-11 集成设计的产品规则。旧文档中的主机、端点和实施状态不能作为当前运行环境依据。

## 2. 用户只需要理解三件事

1. 我正在使用哪个工作区：余额、模型权限和消费归属都跟随它。
2. 我调用哪个模型：工作台和外部 API 使用同一套授权与实际计价规则。
3. 我通过哪里调用：工作台直接使用；外部程序使用自己创建的 API Key。

个人用户默认进入个人工作区；有多个工作区时提供切换入口。登录账号表示身份，工作区表示资源归属，不能按同名账号推断后台绑定关系。

## 3. 职责划分

| 对象 | 职责 | 用户操作 |
| --- | --- | --- |
| Reizo 登录账号 | 身份认证、个人资料、安全设置 | 登录与管理账号 |
| 工作区 | 成员权限、余额、模型授权、消费归属 | 切换、查看、由管理员配置 |
| 后台计费账号 | 承载对应工作区的余额和路由权限 | 由系统维护 |
| 工作台凭证 | 为登录用户的工作台请求提供后台认证 | 用户不用选择或复制 |
| API Key | 为外部程序提供调用认证，可附加限制 | 创建、限制、停用、撤销 |
| 模型目录 | 统一模型标识、可用性、计量单位和价格 | 查看和选择模型 |
| 请求日志 | 记录实际调用、费用和来源 | 按工作台、Key、模型筛选 |

一个工作区绑定一个后台计费账号。工作台凭证与多把 API Key 共用工作区资源；会员额度和充值余额分账记录，遵循第 11 节的扣减规则。创建 Key 不创建独立余额或套餐，也不扩大账号权限。

## 4. 两条调用路径

### 工作台

登录会话 → 校验当前工作区成员身份 → 校验模型权限 → 取得工作台凭证 → new-api 调用与扣费 → 返回结果并记录来源。

用户选模型即可开始对话，不依赖用户是否创建了 API Key。内部凭证由系统创建、检查和轮换。管理页显示“工作台调用”的可用状态和消费入口，不展示内部密钥，也不允许误删。

### 外部 API

Reizo API 地址 + API Key → 校验 Key 状态与归属 → 校验附加限制 → 校验工作区模型权限 → new-api 调用与扣费。

默认 Key 继承账号模型权限和自动路由；添加模型白名单只能收窄权限。工作台和 API 对同一工作区、同一模型适用相同的后台计价规则。

“全部模型”指当前账号已获授权且实际可路由的模型。不能根据门户卡片数量或取消模型白名单，就宣称所有模型都可调用。

## 5. 统一密钥管理

目标是所有归属于当前工作区的外部 Key 均可在 Reizo 管理。当前标注“在 new-api 管理”的展示只是过渡状态。

### 已有 Key 的纳管

- 按已验证的工作区与后台账号 ID 关系导入，不能按用户名匹配或跨账号汇总。
- 使用后台 token ID 去重；工作台凭证单独识别，不重复出现在外部 Key 表格。
- 保留已有名称、状态、有效期、模型限制、IP 限制、路由与额度设置，不能在导入时自动放宽限制。
- 列表展示只是读取元数据。纳管需要建立本地持久映射，保证编辑、撤销、消费统计和调用认证都能定位同一个 token。
- 原有密钥兼容 Reizo API 地址需要单独完成认证映射；不能把“显示在列表”当成“已能用于 Reizo API”。
- 如果保留原密钥调用，导入时仅在服务端读取并加密保存上游凭证、计算认证摘要，不将完整旧密钥重新返回浏览器。
- 导入可重复执行；并发导入不得重复建档。失败时记录同步状态和可重试原因。
- 管理操作按工作区权限执行；上游明确拒绝或超时，不能显示已成功同步。

### 新建 Key

名称为必填，其余限制选填。完整密钥只在成功创建后显示一次。

创建过程需要防重复和补偿：不能因重试生成多把 Key；不能创建上游 token 后本地写入失败，留下用户看不到的可用凭证。同名 Key 不能依赖名字猜测绑定对象。

## 6. 余额、定价和模型权限

- 模型真实用量及适用计价规则是结算依据。会员额度与充值余额需要独立账户及统一结算；不能把同一份上游扣费同时记入两者。new-api 现有能力是否支持该结算模型，需要核对后决定实现位置。
- 普通工作区余额读取使用工作区自己的授权；全局管理凭证用于平台管理操作，避免它失效时拖垮所有用户查询。
- 余额读取失败必须返回“暂不可用/同步失败”状态，不能伪装成 0。
- 门户发布状态与实际可调用状态分开保存：发布不能授予权限；后台已接入且已发布，才可对外宣传为可使用。
- 登录后的模型目录、工作台选择器、API 模型接口共用授权结果。加载失败不能回退到权限更大的服务凭证目录。
- 展示价格由实际计价配置生成，明确币种、输入/输出、计量单位及账号适用倍率。管理页修改计价后，需确认后台写入成功并重新读取。
- 区分“未接入、未授权、暂停服务、暂时不可达”，向用户提供能采取行动的提示。

## 7. 请求日志和消费

统一记录工作区、模型、调用时间、状态、用量、实际费用、调用来源及请求 ID。

来源至少区分“工作台”和具体 API Key。纳管旧 Key 后必须能关联其消费；不能只统计本站新建的 Key。

若后台尚不能可靠识别工作台操作者，先展示工作区级消费，补充请求与成员关联后再提供成员级归因，不能凭共享 Key 猜测操作者。

## 9. 实施顺序与验收

### 第一阶段：稳定工作区边界

统一工作区授权服务、凭证刷新和错误分类；普通余额查询去除全局管理凭证依赖；工作台凭证显示健康状态。

验收：管理凭证失效不影响登录；余额失败不会显示 0；切换工作区不会读取其他工作区资源。

### 第二阶段：所有 Key 在 Reizo 管理

幂等导入现有 Key，支持编辑、停用、撤销和消费关联；验证旧 Key 使用 Reizo API 地址的兼容性；处理创建补偿和同步失败。

验收：重复同步不重复建档；旧限制完整保留；撤销后调用被拒绝；普通成员不能越权；临时测试 Key 可彻底清理。

### 第三阶段：统一模型和实际价格

提供统一目录与授权结果，工作台/API 使用相同模型 ID 和路由能力；门户发布与真实能力核对；价格写入后回读校验。

验收：同一工作区在工作台和 API 可用模型一致；门户选择模型正确进入工作台；无权限模型不会被默认替换成另一模型调用。

### 第四阶段：统一消费体验

余额、请求日志、工作台消费和各 Key 消费均从后台真实数据生成，后台故障以明确状态呈现。

验收：通过可关联的请求 ID 核对实际调用与扣费；不得仅凭模拟测试或可读模型数量宣称真实调用、计价已全部验证。

## 11. 会员额度与充值余额：用户确认的规则

用户于 2026-09-12 确认采用“每月额度池 + 剩余百分比 + 充值余额”的产品形式。

### 展示与计量

- 会员额度按月发放，主要展示本周期剩余百分比和下次重置时间；后台保存精确总量与消耗明细。
- 充值余额以金额展示，按实际模型用量和公布的计价规则结算。
- 百分比由真实剩余额度计算，不作为独立计费单位。示例中的 100,000 点等数值不是已确定套餐。
- 输入、缓存读取/写入、输出，以及图片/视频等对应计量项，经明确的规则换算成额度消耗。
- 第一版不叠加五小时、每周等多个额度窗口。

### 扣减规则

- 优先使用会员额度。
- 用户开启“允许余额继续使用”后，才可在额度不足时使用充值余额；默认不自动转扣余额。
- 同一份用量不能同时扣额度和余额。若一次请求跨越额度边界，需明确定义分摊，明细分别记录两部分。
- 额度和余额决定支付能力，模型权限决定能否访问，Key 仅负责调用认证。

### 实施前仍需确定的参数

- 各套餐月额度总量、额度换算比例，以及会员折扣如何参与计算。
- 周期按订阅起始日还是自然月计算、时区、未用完额度是否结转。
- 不同调用入口的额度适用范围、升降级及续订时的额度处理。

这些参数尚未确定，不能把示例值写入生产套餐。

### 后台实现约束

需先审计 new-api 是否已具备两类账户、扣减优先级及原子结算能力。前端增加百分比并不能完成该改造。

一次请求使用唯一结算标识，结合预留和实际用量结算处理并发、重试、流式输出及中断；失败是否收费以真实上游计费结果为依据。额度按其所属周期结算，跨周期请求不能误扣新周期。

若后台不支持以上能力，补齐结算能力后再上线；不能只在 Reizo 显示两份数字，而后台仍无差别扣一个余额。

## 12. 新网关目标架构

### 已确认方向

- 用户入口和全部用户可见功能集中在 Reizo。
- codex-proxy 是后台模型调用网关，管理界面仅供管理员使用。
- 从 new-api 提取需要的后台功能，逐步替换现有依赖。
- 本次只更新架构方向，没有切换生产流量或修改新网关代码。

### 建议的业务归属

| Reizo 业务层 | codex-proxy 网关层 |
| --- | --- |
| 用户、工作区、成员和套餐权益 | 上游账号、API 渠道、凭据刷新 |
| 会员额度、充值余额、用户结算账本 | 模型路由、协议适配、流式响应 |
| 对用户的销售价格与额度换算 | 并发、限流、来源健康、重试 |
| 用户 API Key 生命周期与附加限制 | 校验受信身份和执行获准的调用范围 |
| 门户展示、工作台、用户消费查询 | 输出真实用量、尝试记录、错误及上游成本信息 |

这张表是结合“网关专注调用”提出的实现分工；资金结算的最终落点仍需在实现前确认，不能只按界面归属推断。

建议用户余额和会员额度只有 Reizo 一个业务账本，网关提供真实用量事件。网关可维护容量和上游配额，但它们不等同于用户购买的会员额度。

### 两者之间的稳定契约

- 使用稳定的工作区 ID、凭证 ID 和请求 ID，不暴露内部 new-api 用户 ID、PAT 或账号分组概念给用户。
- 工作台通过 Reizo 登录态调用；外部 API 通过 Reizo 发放或纳管的 Key 调用。网关执行前必须验证服务端签发的身份与权限，不能信任客户端自报的工作区。
- 模型目录提供模型 ID、能力、协议和可用状态；Reizo 将套餐权限及发布状态叠加到目录上。
- 请求执行前完成额度/余额的准入或预留；网关回传可靠用量事件，Reizo 幂等结算。不能等请求消耗结束后才检查余额。
- 用量区分输入、缓存读写、输出和媒体计量；包含成功、中断、失败、重试及最终费用信息，保留计价版本。
- 事件需可重放、可去重、可对账。一次逻辑请求与多次上游尝试分别标识，避免路由重试引发重复用户扣款。
- 流式请求按实际已发生且应计费的用量结算；结果不确定时进入待核对状态，不能直接当作免费或完成扣费。

### 已查看的新项目资料

README 将项目定位为多账号 AI 网关，说明现有客户端入口为 Responses API，不支持 Chat Completions；docs/source-routing-design.md 描述了 API 渠道与来源路由扩展计划，并明确部分能力仍待实施。以上是文档证据，不能替代运行验证。

迁移前逐项核对 Reizo 实际使用的文本、图片、视频等协议和功能，按能力迁移；不能仅替换网关地址就宣布全部接入。

### 调整后的实施顺序

1. 明确身份、Key、模型目录、价格与用量结算契约，以及用户账本的唯一归属。
2. 将 Reizo 对网关的访问收拢到适配层，当前 new-api 接口作为过渡适配器。
3. codex-proxy 接通一个模型的完整调用、权限与用量回传流程，在隔离测试中核对结算。
4. 逐项迁移模型能力及已有 Key；保留凭证兼容策略和回滚路径，避免打断用户已有程序。
5. 完成权限、用量和账本对账后，按受控范围切换生产流量；确认无依赖后再下线 new-api。

迁移期间只允许一套生产结算规则生效；影子验证不二次扣费，也不未经控制地重复发送付费模型请求。

## 13. 2026-09-12 第一批实现

- 新增 WorkspaceGateway 应用接口和过渡适配器，收拢 Key 管理及工作区余额读取；未实现的后台类型拒绝启用。
- 账户、钱包和消费汇总使用工作区授权读取余额，不再依赖全局管理凭证；钱包区分同步失败与真实零余额。
- 新增历史 Key 纳管接口：校验工作区管理权限，事务与工作区锁保证重复导入不会重复建档；保留原密钥认证摘要、加密凭证、状态及限制。
- 纳管后的 Key 在 Reizo 编辑、启停、撤销，旧密钥可通过已有的摘要认证机制使用 Reizo API；编辑不会清除原路由配置。
- 撤销需先得到网关确认，再报告成功。
- Key 页面显示工作台凭证状态；工作台调用检查当前成员关系、本地凭证状态与有效期。
- 新增月度额度类型、待配置状态、默认计费配置及精确百分比计算，钱包将会员额度与充值余额分开展示。

本批未切换 codex-proxy，也未启用额度扣减或建立新的资金账本。配置模型尚未接入可编辑的持久化计费配置；套餐数值、周期策略及新网关的可靠结算接口仍待落实。推理、完整模型目录、平台管理定价等接口仍有旧适配依赖，需要按第 12 节继续迁移。
